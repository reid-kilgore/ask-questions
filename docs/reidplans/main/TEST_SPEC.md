# Test specification

The focused test suite verifies command argument rules, payload validation rules, keyed response validation, lexical and symbolic-link document path containment, and the required command help topics. Help coverage includes the long human response wait, the lack of a built-in answer timeout, the blocked lifecycle, the caller execution-timeout rule, and the fact that normal waiting is not a failure. It starts no-browser command sessions, reads URLs from standard error, submits and cancels through HTTP, and verifies the keyed JSON results and exit codes. The integration test stops its child process if URL discovery, HTTP submission, an assertion, or a timeout fails.

Browserless checks verify the interface contract through static source assertions where practical, including Focus mode as the initial view. Manual review starts in Focus mode, then covers the existing all-question toggle, focused Previous and Next actions, non-blocking focus navigation, final-review required validation, review-page summary, Other-input visibility, completion states, and stable layout behavior.

Manual review also verifies **Copy as JSON** from the final review page. It must copy a submitted-result envelope without sending a request. A required blank or whitespace-only answer must return the user to the first missing focused question. After the command process stops, the already-loaded review page must still copy the current result JSON. This is a clipboard recovery check, not a persistence test.

Manual test: run `npm install`, then `npm link`, then `ask-questions --file examples/request.json`. Confirm that the session starts in Focus mode, switch to All questions through the existing toggle, and review the non-blocking focused Previous/Next flow, Command or Control plus Enter, final-review validation, Other-input visibility, the fixed document pane, entered answers and notes, the HTTP-200 completion state, and the single keyed JSON line on standard output.

## Scope addendum: request origin and ready sound

Focused checks verify that the ready sound defaults to enabled, `--no-ding` disables it, `--ding` enables it, and the last sound option wins. They verify that help, including both sound options, does not write to standard error. Normal server integration tests explicitly use `--no-ding` and do not play a sound. They verify the derived `askerPath` in browser session data and in submitted and cancelled JSON results, including rejection of a payload-provided path. Static interface checks verify an Asked from path element, safe `textContent` rendering, and copy handling. Isolated tmux tests inject a command function to check a successful window-name result and a failed lookup without a real tmux server.

Manual test: run `ask-questions --file examples/request.json`. Confirm that the page URL appears before the default ready sound. Run again with `--no-ding` to confirm silence. Confirm that **Asked from** shows the full invocation directory and wraps safely on a narrow page. Start the command in a tmux window to confirm that its window name appears when tmux returns one. Submit and cancel separate sessions to confirm that `askerPath` is in each final JSON result and `askerTmuxWindow` is present only when found.

## Scope addendum: Markdown message

Integration coverage starts a no-browser session with a Markdown `message` and inspects session data. It verifies headings, lists, emphasis, code, and safe external links in `messageHtml`. It also verifies that raw HTML is not emitted as an HTML element and that an unsafe link never has an unsafe `href`. Browser source coverage verifies that the message container uses only server-rendered `messageHtml` for HTML insertion. Help coverage tells agents that `message` accepts Markdown and can hold relevant context.

Document-help coverage verifies complete inline Markdown and relative-path Markdown payload examples, unique non-empty document ids, non-empty document titles, exactly one content source, and both path bases. Help-example coverage extracts only the Examples section, expects four displayed JSON payloads, parses and validates each payload, and verifies that each contains at least two questions. It also validates the multi-question `examples/request.json` file. One-question integration fixtures remain valid coverage because batching is optional. Static layout coverage verifies that the tab grid does not have a maximum height or internal vertical scrollbar, and document content keeps the wide-screen internal vertical scrollbar.
